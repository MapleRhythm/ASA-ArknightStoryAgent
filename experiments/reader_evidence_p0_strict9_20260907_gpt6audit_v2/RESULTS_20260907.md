## 结论先行

这不是全系统线上回答正确率，而是固定证据条件下、9 个问题族 × 3
evidence condition 的 reader 诊断。

当前 clean-SFT 4B 的 GLM evidence-only 语义审计结果为：

- 完整且受当前证据支持：`7/27 = 25.9%`
- `actual_prompt`：`3/9 = 33.3%`
- `minimal_sufficient`：`2/9 = 22.2%`
- `sufficient_with_distractors`：`2/9 = 22.2%`
- 集合判定：`partial 13/27`、`contradicted 3/27`、`none 4/27`
- 当前可见证据在人工协议中全部标为充分；GLM 审计也判定 `27/27` 的
  `context_sufficiency=sufficient`
- 动作 appropriateness：`22/27 = 81.5%`；剩余 5 条是在证据充分时错误地
  `retrieve_more`

因此，当前首要问题不是“模型不会输出动作”，而是**在证据已经足够时，
仍只生成部分答案、重复事实、夹带无关或矛盾事实**。

## 原始 4B 的特殊问题

原始 4B 的 27 条输出全部在 768 token 上限结束，全部包含
`<think>...</think>` 长推理，而不是 canonical Exx JSON：

- generation truncated：`27/27`
- strict JSON：`0/27`
- schema valid：`0/27`
- GLM audit eligible：`0/27`

这说明原始 4B 对当前 non-thinking Exx 协议存在明显模板/停止条件不兼容。
它可以作为“当前协议下失败”的证据，但不能据此断言原始模型的阅读语义能力
为零。下一轮必须先修复 base reader 的 thinking 开关、assistant prefix、
EOS/stop 和实际 chat template，再做公平 adapter 对照。

## 失败模式

1. **证据足够却继续检索。**  
   `dd12b4f...` 和 `eb0d4f...` 在 minimal/distractor 条件各有两条
   `retrieve_more`。GLM 判定当前上下文充分，因此这 4 条不是安全拒答，而是
   过度检索。

2. **重复事实是主要协议缺陷。**  
   clean-SFT 的 duplicate rate 在 minimal 为 `1/9`，加入真实同场景干扰后
   升至 `3/9`；actual 为 `4/9`。这直接将 schema valid 从 `8/9` 和 `6/9`
   拉低，且与相关性膨胀同时出现。

3. **难例上的主体/关系绑定仍不稳定。**  
   `ffc93a...` 三个条件均被审计为 `contradicted`，说明不是简单的证据缺失，
   而是把“谁认为谁是叛徒”的关系绑定错了，应作为 hard-negative/关系监督
   样本。

4. **干扰证据增加无关内容。**  
   clean-SFT 在 answer rows 中的 irrelevant rate 为：minimal `2/7`、
   distractors `3/7`、actual `1/9`。本轮样本很小，但方向与“证据支持不等于
   问题相关”一致。

## 判断与下一步

当前 clean-SFT **格式能力已经基本可用，但回答语义正确率不足**；不能直接
进入 RLVR 或把这组结果宣传为线上准确率。

建议顺序：

1. 先修复原始 4B 的 canonical non-thinking 推理协议，并重新跑同一 27 行；
2. 在 clean-SFT 上增加“必要事实一次且只说一次”的输出约束和训练样本，
   对重复事实、无关事实、主体/时间/否定错配设置明确负例；
3. 单独校准 evidence-sufficient controller，减少充分证据下的
   over-retrieve；对 `retrieve_more` 不能只按动作格式给奖励；
4. 用 `ffc93a...` 这一类关系矛盾题构造主体-关系 hard negatives，并让
   verifier 检查联合事实而不是只检查单条 E-ID；
5. 完成以上修复前，不改生产 MiniRAG 默认、不启动正式 RLVR；继续保留
   frozen runtime 作为 A/B 基线。
