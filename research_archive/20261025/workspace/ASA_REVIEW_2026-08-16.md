# ASA 系统设计与效果评审

日期：2026-08-16

## 结论摘要

ASA 当前的高弃答率和幻觉不是单一模型问题，而是三个环节叠加：

1. 检索到的候选证据经常不完整，模型在生成前就缺少回答所需事实。
2. 旧 reranker 数据存在标签污染和评测泄漏，离线高分不能可靠代表新故事或线上查询。
3. 旧 grounding 分支允许未验证文本通过兜底路径进入答案，引用存在不等于主张被证据蕴含。

本轮完成了 E-ID 紧凑引用与服务端验证改造，并建立了按故事族隔离的 reranker 数据和盲测流程。新 reranker 在合成排序盲测上有提升，但在真实全链路盲测上头部排序退化，因此没有替换线上模型。

## 系统链路判断

当前主链路可概括为：

查询 → Dense/BM25/MiniRAG 多路召回 → 融合与邻居扩展 → Cross-Encoder 重排 → 证据提示词 → 答案生成 → Grounding 校验/兜底。

效果问题的优先级如下：

### P0：证据覆盖不足

既有评测中，进入生成提示词的前 12 条证据能完整覆盖 gold evidence 的比例约为 42%，约 58% 的问题在生成前证据已不完整。此时单纯加强拒答规则会降低幻觉，但必然继续抬高弃答率。

因此需要把“没有答案”和“检索不完整”分开记录。后者应触发查询分解、扩大候选、故事/章节路由或定向二次检索，而不是直接拒答。

### P0：Grounding 兜底会绕过验证

旧路径在结构化校验失败时，可能回退到模型原始文本或未验证片段。这样即使主流程要求引用，错误主张仍可能从兜底分支进入最终答案。

本轮已在 E-ID 模式中禁止该行为：验证失败时只返回固定弃答，不再输出原始模型文本。

### P1：Reranker 训练分布与线上候选不一致

旧 v6 数据共 3841 对，其中至少包括：

- 709 条 `shuffled_order`：只是把同一组证据换序，却被标为负例；
- 21 条弱 gold；
- 110 条负例实际覆盖了全部 gold 信息；
- 大量模板化负例，真实线上失败样本比例偏低；
- 原有 failure-hard 集合与训练集高度重叠，不能作为盲测。

这会让模型学习模板和顺序偏好，而不是学习“这组证据是否真正支持问题”。

## E-ID 紧凑引用方案

建议保留完整证据给模型阅读，但要求模型只输出原子主张和证据编号：

```json
{
  "facts": [
    {"claim": "原子事实", "evidence_id": ["E3"]}
  ]
}
```

最终展示可以只显示 `[E3]`，无需重复证据全文。节省输出 token 是附加收益，真正降低幻觉的是服务端验证和重建答案：

- 只接受提示词中实际存在的 E-ID；
- 每条主张最多绑定 1–2 个证据；
- 限制主张数量和长度，强制原子化；
- 禁止模型自行输出 `inferred` 内容；
- 检查主张与证据的词项覆盖；
- 对母亲、父亲、动机、幕后主使等敏感关系词做额外一致性检查；
- 服务端从通过验证的 facts 重建答案，不信任模型给出的 `final_answer`；
- 任一关键校验失败时固定弃答，禁止 raw fallback。

该方案能可靠拦截“引用不存在”“引用错编号”“敏感关系凭空出现”等错误，但当前词项检查仍不等同于语义蕴含。后续还需要 claim-evidence NLI/LLM verifier 来判断否定、主体互换、因果方向和时间关系。

## Reranker 数据与训练

### 干净拆分

按去除 `_partNN` 后的故事族拆分：

- 训练：14 个故事族，533 个 listwise 查询；
- 验证：4 个故事族，116 个查询；
- 测试：6 个故事族，139 个查询；
- train/val/test 的精确 query、source-query 和故事族交集均为 0。

清洗后基础 pairwise 数据：

- train：1995 对 / 515 个原始查询，构建后覆盖 533 个 listwise 查询；
- val：398 对 / 108 个原始查询；
- test：472 对 / 129 个原始查询。

从真实生产检索候选中挖掘了 2102 条 hard negatives（chain 1019、document 1083），经过误负例过滤和去重后，最终训练集为 3151 对、533 个查询。

### 盲测结果

合成 pairwise/listwise 测试：

| 模型 | Pairwise Acc | Listwise Top-1 | Listwise MRR |
|---|---:|---:|---:|
| 原始 BGE 基座 | 88.14% | 38.85% | 0.6396 |
| v7 clean stage1 | 91.31% | 38.85% | 0.6570 |

真实召回、融合、邻居扩展、重排全链路测试：

| 模型 | MRR | R@1 | R@5 | R@32 | 完全漏检 |
|---|---:|---:|---:|---:|---:|
| 原始 BGE 基座 | 0.6017 | 50.36% | 73.38% | 85.61% | 20/139 |
| v7 clean stage1 | 0.5929 | 49.64% | 71.22% | 87.05% | 18/139 |

结论：v7 学到了更强的成对判别和较深召回能力，但损伤了头部排序；当前版本不应部署。加入线上 hard negatives 的 stage2 退化更明显，也不应部署。

按查询类型看，候选主要改善 causality 和 reasoning，明显损伤 fact 和 reveal。基于本次测试做事后类型路由，理论上可得到约 MRR 0.6234、R@1 53.24%，但这是测试集上的事后选择，必须用新的盲测集验证，不能直接作为上线结论。

## 对 Claude 与 DeepSeek 论断的判断

两者正确的方向包括：

- 需要真实 hard negatives，而不是继续堆模板负例；
- 必须按故事/文档族拆分，避免 query 或 source 泄漏；
- 证据应使用受约束的 ID，并由服务端验证；
- reranker 不能代替候选召回覆盖。

需要修正或补充的部分：

- “增加数据重训”不必然改善排序；错误标签和候选分布不一致会让端到端结果变差。
- 只把证据正文改成 E-ID 只能节省输出长度，不能自动消除幻觉；关键是原子主张校验、服务端重建和禁用未验证兜底。
- v6 在旧验证集上的极高分数受训练重叠影响，不能作为泛化能力证据。
- 评审 reranker 必须以最终融合后的线上候选列表为单位，而不是只看合成 pairwise 指标。

## 推荐改进路线

### 第一阶段：先降低幻觉，不额外抬高弃答

1. 将 E-ID 分支以小流量 canary 上线，记录引用 ID 有效率、主张通过率和各类失败原因。
2. 把弃答拆成 `no_candidate`、`incomplete_evidence`、`invalid_citation`、`unsupported_claim`、`generation_failure`。
3. 对 `incomplete_evidence` 启动查询分解和定向二次检索；只回答已支持部分，并明确未覆盖部分。
4. 增加语义蕴含校验，重点覆盖否定、身份关系、因果方向、时间顺序和主体互换。

### 第二阶段：重新定义 reranker 训练任务

1. 从最终 fusion top-80/top-120 候选直接构造 listwise group，而非脱离线上分布的独立负例。
2. 同时加入正确 chain 与其对应正确 document 作为正例，避免模型只会给 chain 打高分。
3. 使用 group softmax/ListMLE，并把最终 fusion score 一并校准；评价指标直接使用端到端 MRR、R@1、R@5 和 evidence completeness。
4. 加入基座蒸馏或 KL 约束，防止 fact/reveal 能力灾难性遗忘。
5. 针对 causality/reasoning 做专家适配，再蒸馏回单模型；双模型路由仅作为验证工具，避免线上双倍显存和延迟。
6. 每次训练保存并恢复最佳验证 checkpoint，禁止默认使用最后一轮权重。

### 第三阶段：改进召回与可观测性

1. 建立故事、章节、角色、事件四级路由和实体别名归一化。
2. 对多跳问题先生成子问题，再做覆盖率驱动的证据集合选择。
3. 动态调整 top-k：短事实问题收紧，因果/揭示/推理问题扩大并保留相邻剧情块。
4. 仪表盘至少跟踪：候选覆盖率、prompt evidence completeness、claim support rate、citation validity、abstain reason、各 query type 的 MRR/R@k、P50/P95 延迟。

## 运维风险

248 是较旧的无 Git 镜像，A100 当时被其他任务占用，不宜作为项目真源。建议以可审计 Git 分支和版本化模型清单作为唯一发布来源。
