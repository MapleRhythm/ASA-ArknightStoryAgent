T1: 增强 reranker 的 chain 内部结构感知

  当前做法：chain 文本连起来输入 reranker，打一个分。链内顺序靠 shuffled_order 负例学。

  问题：shuffled_order 与 gold 的差异只是前/后调换，语义几乎相同。reranker
  容易靠表面词匹配区分，忽略因果结构。

  优化：在 listwise 训练时，给每条 chain 加上 chain structure metadata 作为额外输入：
  # 在 reranker 的 input 里增加：
  {
    "query": "...",
    "chain": "[E11] ... [E13] ... [E14] ...",
    "chain_metadata": {
      "chain_length": 3,
      "has_action": true,      # 是否有 action/motive evidence
      "has_outcome": true,     # 是否有 outcome evidence
      "has_context": false,    # 是否含纯背景
      "causal_order": "action→conclusion",  # 顺序类型
      "evidence_types": ["motive", "outcome", "bridge"]  # 每节的类型
    }
  }

  这让 reranker 学到"action→outcome→conclusion 链"比"outcome→action→conclusion"更好，而不只是"这三个
  evidence 凑一起挺好"。

  数据：从 answer_focus 字段里提取每个 E-ID 的语义类型（motive/outcome/context/bridge），用 Claude
  教师自动标注（教师本来就知道哪些 E 是动机、哪些是结果），不需要人工。

  实现：修改 evidence_chain_dataset.py 的 build_reranker_listwise_record，在 candidate 里增加
  chain_structure 字段。reranker 输入模板改成：
  [QUERY] {query}
  [CHAIN_LENGTH] {chain_length}
  [CHAIN_STRUCTURE] {causal_order}
  [EVIDENCE_TYPES] {evidence_types}
  [CHAIN] {chain_text}

  T2: 给 4B 的 conclusion 加"证据缺口感知"训练

  当前做法：conclusion prompt 里写 19 条软规则，模型靠猜。

  问题：教师在生成 conclusion 时，evidence 是否完整是不可观测的。教师可能生成"answer_directly"但 evidence
  其实不够，4B 学到了错误的 abstain 行为。

  优化：用自动证据缺失检测给 conclusion 样本打标签：
  def judge_conclusion_quality(question, answer, evidence_texts, gold_chain_text):
      # 如果 answer 中的 key claim 词在 evidence 里命中率 < 0.6 → 标记为 "abstain_should"
      # 如果 answer 只覆盖了 partial chain（缺少 motive 或 outcome）→ 标记为 "answer_directly_but_partial"
      # 如果 answer 正确且完整 → 标记为 "answer_directly_good"

  用 Claude 教师跑这个判断，给 SFT conclusion 数据加 meta.conclusion_quality 字段。然后在 system prompt
  里明确告诉 4B：

  你是 conclusion_synthesizer。
  如果当前证据存在以下情况，必须输出 abstain：
  1. 证据中的 action/motive 和 outcome 缺失任一
  2. 答案中的关键实体在证据中出现率 < 60%
  3. 证据为纯背景，无角色对话或具体事件

  如果满足以下条件才可 answer_directly：
  - 证据覆盖了 answer 的所有关键 claim
  - 证据包含至少一个动机/原因类 statement
  - 没有未解决的指代歧义

  这比"19 条软规则"更可执行，且有数据支撑。

  T3: 4B 的 retrieval decision 加"主动澄清"能力

  当前数据问题：从 SFT 数据看，clarify_user 样本比例偏低。大多 retrieval_decision 是 retrieve_more 或
  answer_directly，clarify_user 少。

  优化：在生成 SFT 数据时，专门注入"歧义触发"样本：
  - 问题含代词（他/她/它/这位/那位）且对话上下文不足以消歧
  - 问题涉及多个同名实体（戈尔丁女士出现多次）
  - 问题涉及隐喻或双关

  让教师在 evidence 里故意不放消歧证据，迫使 4B 学会主动要求澄清，而不是硬答或反复检索。

  T4: hypothesis_generation 的关键词质量

  从 SFT 数据看，keywords 经常是问句词的重复（如 "帮助阿斯卡纶","进城"），缺乏实体消歧词和关系桥接词。

  优化：在 hypothesis_generation 的 system prompt 里加规则：
  keywords 必须包含：
  1. 问句中的核心实体（已在 entities 中）
  2. 该实体的**下位概念词**（比如问"凯尔希"→"凯尔希医生/Rhodes Island 医疗总监"）
  3. 该实体所属的**上位类词**（比如问"凯尔希"→"罗德岛高层/医疗组织"）
  4. 如果问动机/原因，还要包含"原因/动机/目的/背景"类词

  这些词直接进入 BM25 和 dense query，决定了是否能召回到正确文档。

  T5: 双向 reranker（用 retrieval recall 信号做 SFT 数据过滤）

  当前缺失：没有用召回评估的结果反向过滤 SFT 训练数据。

  具体做法：
  1. 用当前的 evaluate_retrieval_recall.py，对每条 SFT 样本的 question，在 inference pipeline
  里跑一遍，看召回是否命中 gold
  2. 如果 recall@5 = 0（前 5 个结果里 gold 完全不见），说明这条 SFT 样本的 evidence 本身就不可达
  3. 标记这些样本，从 SFT 数据里剔除或降权

  这样 4B 不会学到"evidence X 能回答问题 Y"但 inference 时 X 永远召不回来。

  T6: Teacher prompt 的 evidence selection 优化（上游水源）

  这是最重要的但改动最大。教师生成 SFT 数据时，evidence 是怎么选出来的？

  从 sft_teacher_generation.json 看：
  "evidence_mode": "retrieval",
  "retrieval_top_k": 3,
  "max_evidence_docs_per_request": 3

  教师只见到 3 个 top-k 检索文档。如果这些文档恰好不包含关键 chain
  evidence，教师就会生成"看似合理但实际错误"的 hypothesis/conclusion。

  优化：把 retrieval_top_k 从 3 增加到 6-10，让教师见到更多候选文档，由教师自己判断哪些组成有效
  chain。这样生成的 hypothesis 里的 keywords 更有覆盖性。

A1. GraphRAG / LightRAG（强烈推荐，长期高 ROI）
  
  微软 GraphRAG（2024）思路：用 LLM 抽取实体-关系-社区，构建多层级知识图谱，问答时做"局部子图 →
  全局摘要"两路融合。本项目天然适配：
  - 角色、组织、地点、活动都是命名实体
  - "凯尔希、阿米娅、特蕾西娅"间的关系图在剧情里反复出现
  - 召回时按"实体 → 关系链 → 故事 chunk"三层定位，事实题（r@1 16%）直接受益
  
  适配做法：
  - 用 Minimax 教师从每段剧情抽取 (head, relation, tail, source_chunk_id) 三元组
  - 建立 NetworkX 图 + 实体倒排索引（已有 operator_aliases.json 是雏形）
  - 问"X 是 Y 什么人" → 图查询直接返回 (X, relation, Y) + 证据 chunk
  - 用 LightRAG（HKU 开源，2024-10）轻量实现：单文件 ~2000 行，比 GraphRAG 简 10×
  
  预期：fact/relation 类 recall@1 可从 16-26% 提升到 40%+
  
  A2. HippoRAG / HippoRAG 2（OSU，2024）

  仿海马体记忆机制：PageRank over knowledge graph。每个 query 用 LLM 抽实体 → 在图上做个性化 PageRank →
  高分节点对应的 chunk 进入候选。
  - 比 GraphRAG 更适合多跳问题（你的 reasoning/reveal/causality 占 65%）
  - 论文报告多跳 QA recall 提升 20pp 

  A3. MiniRAG（HKU，2025-01）
  
  你提到的方案。专为小模型设计：
  - 用异构图把 chunk 和实体放同一张图（chunk-node + entity-node）
  - 召回时按图传播；不需要大模型做实体抽取（关键，你的 4B 抽取质量有限）
  - 在 1.5B 模型上比传统 RAG 提升 10-20pp

  与本项目契合度：4B 模型偏小，正是 MiniRAG 的目标场景；现成的 documents.jsonl 可直接做 chunk-node。

  A4. ColBERTv2 / late interaction

  传统 dense retriever 把 query 压成一个向量，丢细节。ColBERT 做 token-level 匹配：
  - 每个 query token 与每个 doc token 做最大内积
  - 对"凯尔希、太师、身份"这种多锚点 query 友好
  - 已有开源中文权重（如 bge-colbert）

  成本：替换 dense retrieval 那条线；索引比 FAISS 大 ~10×（53k chunk → 大约 8GB）

  A5. Hierarchical Chunking + Auto-Merging（LlamaIndex 范式）

  - 父 chunk = 整段对话/场景（2000 字）
  - 子 chunk = 单句/单回合（150 字）
  - 检索小 chunk，召回时返回父 chunk
  - 对剧情连续性敏感的 reasoning/reveal 题特别有用

  成本：改 story_parser.py，索引翻倍
  
  A6. Query Rewriting + HyDE 已部分在做

  hypothesis_generation 本质就是 query rewriting + HyDE。可加：
  - 多查询并行（Multi-Query RAG）：4B 生成 3 个不同侧重的 query，分别召回再融合
  - Step-back prompting（DeepMind）：先把 query 抽象成上层问题（"凯尔希的种族" →
  "凯尔希这个人物有什么基本属性"），再下钻

  ---
  第二类：RAG 推理控制范式（强项目契合）
  
  B1. CRAG (Corrective RAG)（推荐，立刻可做）
  
  ICLR 2024。核心：在生成前用一个轻量评估器判断证据质量，分三档：
  - Correct（>阈值）：直接用
  - Ambiguous（中间）：refine（拆分、过滤）
  - Incorrect（<阈值）：fallback to web/external

  与本项目契合：
  - 你的 reranker 评分本身就是 evidence quality 信号
  - conclusion 的 retrieve_more/abstain 决策就是 CRAG 的输出
  - 缺的是显式的"重写 query 再查"环节
  - 把 retrieve_more 路径改成"先用 4B 重写 query，再二次召回"，是 CRAG 思路的最小落地
  
  预期：推理乱答率显著降低，因为弱证据被显式过滤而不是被模型硬答
  
  B2. Self-RAG（华盛顿大学，NeurIPS 2024 best paper）

  模型用特殊 token 自标注：[Retrieve] [Relevant] [Supported] [Useful]。
  - 训练数据需要这些 reflective token
  - 4B 模型在生成时主动判断"我现在需要检索吗"、"这段证据相关吗"
  - 完美匹配你的 hypothesis/retrieval_decision/conclusion 三阶段流程

  做法：把 Minimax 教师生成的 SFT 数据加上反思 token 标注，重训 4B。

  成本：教师 prompt 改造 + 一轮 SFT。这是最贴本项目的范式。

  B3. DRAG (Differentiable RAG) / RA-DIT

  Meta 2023。端到端联合训练检索器和生成器：
  - 用生成器的 loss 反传给检索器
  - 让 dense embedder 学会"被生成器喜欢"的召回偏好
  
  适配难度高：需要把 retriever 也作为可训练模块。短期内不推荐，除非愿意花 ~2 周改架构。
  
  B4. FLARE (Forward-Looking Active Retrieval)
  
  CMU 2023。生成时如果遇到低置信 token，中途触发检索：
  - 模型生成"凯尔希原本是..."，下一个 token 概率分布很平 → 触发检索
  - 拿回来证据再续写
  
  适合需要事实补全的场景。本项目的"多轮 retrieve_more"已是粗粒度版本，FLARE 是 token 级。
  
  B5. IRCoT (Interleaving Retrieval with CoT)
  
  ACL 2023。让 CoT 的每一步都触发检索，而不是先 CoT 完再生成答案。
  - 你的当前流程是"一轮检索 → 出 conclusion"
  - IRCoT 是"出一句 reasoning → 检索一次 → 出下一句 reasoning → ..."
  - 对 reveal/causality 类多跳问题收益大

  ---
  第三类：训练范式增强
  
  C1. DPO / KTO 偏好对齐 reranker 和生成器（推荐）

  SFT 只学"教师怎么答"，DPO 学"哪些答案更好"。具体：
  - Reranker DPO：你的 listwise 数据天然是偏好对（gold > shuffled_order > background_only），可以从
  pairwise 升级到 DPO loss
  - Generator DPO：教师生成两个 conclusion（一个 grounded、一个 hallucinate），让 4B 学会偏好 grounded

  预期：直接降低 hallucination；reranker 排序更稳

  C2. Process Reward Model (PRM)（OpenAI，o1 路线）
  
  不只是评估最终答案，而是评估每一步：
  - step1: hypothesis 生成质量
  - step2: 检索是否到位
  - step3: conclusion 决策是否正确
  - step4: answer 是否 grounded
  
  教师同时生成"好步骤/坏步骤"对，用 PRM 给每个中间产物打分。
  成本：高，但对 agent-style 多步推理收益最大。

  C3. 知识蒸馏：Minimax → 4B 的 thought distillation
  
  你现在的蒸馏是"output 蒸馏"（直接学教师的 JSON 输出）。可以升级：
  - Reasoning Distillation：教师 prompt 加 "先输出推理过程，再输出 JSON"，把推理过程也作为训练目标
  - Soft Label Distillation：教师给每个候选 action 的概率分布（answer_directly: 0.6, retrieve_more: 0.3,
  abstain: 0.1），4B 用 KL loss 拟合
  - Specialized Distillation：四个任务各蒸馏一个 LoRA
  adapter（hypothesis-LoRA、conclusion-LoRA、...），推理时动态切换

  C4. Curriculum Learning

  按难度分级训练：
  - easy: fact 类
  - medium: relation/causality
  - hard: reveal/mystery/answerability + 多跳
  
  教师生成时已经有 difficulty 字段，未充分利用。改训练 loader 按 epoch 渐进采样。

  C5. Contrastive evidence chain learning

  针对你的 reranker：
  - 现在只学"gold > negative"
  - 加 InfoNCE：在一个 batch 内做 all-pairs 对比，让 gold 同时拉远所有 negative
  
  ---
  第四类：推理时增强（零训练成本）
  
  D1. Self-Consistency（最便宜）

  同一个 query 跑 N 次（温度 0.7），投票选 next_action。
  - 推理乱答的本质是单次采样不稳定
  - 5 次投票能消除 80% 的随机错误
  - 成本：推理变慢 5×（可以只对 conclusion 阶段做）

  D2. Reranker Ensemble

  - BGE-reranker（你已有的）
  - Cohere rerank-multilingual（API）
  - 自训的 evidence chain reranker
  三个分数加权融合。短期最快。

  D3. Lost-in-the-middle 缓解

  研究表明 LLM 对 context 中间部分敏感度低。当前你给 4B 的 evidence 是"按 rerank score
  排"。改成"金字塔结构"：
  - top1 evidence 放最前
  - top2 放最后
  - top3+ 放中间
  - 答题时 4B 更易抓到关键证据
  
  D4. MMR (Maximum Marginal Relevance) 选 evidence
  
  当前 prompt_evidence_top_k=12 是直接取 rerank top-12。改用 MMR：
  - 平衡 relevance（与 query 相关）和 diversity（与已选 evidence 不重复）
  - 避免 12 个 chunk 都讲同一句话的不同变体
  - 对 chain reasoning 类问题特别有用

  第五类：数据范式增强
  
  E1. Synthetic Question Generation from KG

  基于 A1 的 KG，自动生成训练 query：
  - 三元组 (凯尔希, 是, 罗德岛医疗总监) → "凯尔希是什么职位"
  - 长链 (A→B→C) → "为什么 A 导致 C"

  绕开"教师 prompt 决定 query 分布"的瓶颈。
  
  E2. Active Learning loop
  
  用 evaluate_retrieval_recall.py 的失败样本回流：
  - recall@5=0 的 query 自动送回教师，让教师重新生成 hypothesis 和 chain
  - 这些 hard 样本进 SFT v3
  
  E3. Negative Sample Mining
  
  现在的 negative 是教师"想象"出来的。改成：
  - 用当前 retriever 召回 top-20
  - 从 top-20 里挑非 gold 的作为 hard negative
  - 这是 in-domain hard negative，比合成 negative 强很多

  E4. Multi-modal evidence（远期）
  
  明日方舟有语音、立绘、PV，剧情解读时玩家会综合考虑。如果未来要扩展，可以引入：

  - 角色立绘描述（VLM 描述生成）
  - 场景图（场景间转移关系）

  CRAG 的完整定义（ICLR 2024）
     
  Query → Retrieve → 【Evaluator】判证据质量 → 三种分支：
                         ├ Correct   → 直接生成
                         ├ Ambiguous → 【Knowledge Refinement】拆解 + 过滤 + 重组证据
                         └ Incorrect → 【Knowledge Search】查 Web/外部知识
                              ↑
                         【Query Rewriting】 把 query 改写成更易召回的形式

  四个核心组件：
  1. Retrieval Evaluator（评分器）—— 判证据 correct/ambiguous/incorrect
  2. Knowledge Refinement（证据精炼）—— 把召回到的长 chunk 拆成 strip → 单独打分 → 过滤掉 noise strip →
  重组
  3. Query Rewriting（查询重写）—— evaluator 判定证据不够时，触发重写
  4. External Search（外部搜索）—— 重写后的 query 去找新知识源

  你项目里有什么、缺什么

  CRAG 组件: Retrieval Evaluator
  你的项目对应: BGE-reranker 输出分数 + 4B conclusion 的 next_action 判断
  完成度: ✅ 有（且更精细：四档而非三档）
  ────────────────────────────────────────
  CRAG 组件: Knowledge Refinement
  你的项目对应: ❌ 没有。你 prompt 直接喂整段 chunk
  完成度: ❌ 缺
  ────────────────────────────────────────
  CRAG 组件: Query Rewriting
  你的项目对应: 4B 生成 follow_up_hypothesis（keywords/entities）
  完成度: ⚠️  半有（只改 keywords，不改自然语言 query；且只在 retrieve_more 后触发，不是 evaluator 触发）
  ────────────────────────────────────────
  CRAG 组件: External Search
  你的项目对应: ❌ 没有（也不需要——剧情 corpus 是封闭世界）
  完成度: ➖ 不适用
  
  关键差异：你不是 CRAG，是 "Multi-round RAG with self-judged hypothesis refinement"
  
  你的 4B 做的是整轮重新检索（hypothesis → query → retrieve → conclusion 全跑一遍）；CRAG 做的是对已召回的
   chunk 做内部精炼（不重跑检索，而是把 chunk 切碎重组）。

  举个对比：

  场景: 召回到 12 个 chunk，其中 8 个是背景、4 个含答案
  你的做法: conclusion 看完 12 个 → 决定 retrieve_more → 改 keywords 重查
  CRAG 做法: evaluator 给 12 个 chunk 单独打分 → 砍掉 8 个低分 → 把 4 个高分 chunk
    进一步切成句子，再砍噪声句 → 重组送生成器
  ────────────────────────────────────────
  场景: 召回完全错（top-12 都是无关章节）
  你的做法: retrieve_more + 改 hypothesis
  CRAG 做法: rewrite query + 外部搜索

  所以"CRAG-lite"在你项目里要补的是什么
  
  我之前 Sprint 1 提到的 "CRAG-lite" 其实是这几件事：
  
  1. Knowledge Refinement（你完全缺） — 收益最大
  
  - 把 rerank top-12 的每个 chunk 按句子切（你已有 LINE_SPLIT_RE）
  - 每个句子用 reranker 单独打分（reranker 可批量推理，开销不大）
  - 把每个 chunk 内的低分句子砍掉，只保留 top-3 句
  - 重组成"精炼证据包"再喂给 4B
  - 预期：4B 的 context 噪声减少 60%+，hallucination 直接下降
  
  2. Query Rewriting 的真正自然语言重写（你只做了一半）

  你现在 follow_up 只改 entities/keywords，原始 question 不变。CRAG 是：
  - 把 "凯尔希是谁" 重写成 "凯尔希在罗德岛担任什么职位？她的种族和身世背景如何？"
  - 重写后的 query 进 dense retrieval 时语义更丰富
  - 做法：让 4B 在 follow_up_hypothesis 里多输出一个 rewritten_question 字段

  3. Evaluator 显式三档化（你是隐式的）

  你的 reranker 输出连续分数，conclusion 输出离散 next_action，中间没有显式的 evidence 质量分档。改成：
  - 计算 top-k rerank score 的均值/方差
  - 高均值 + 低方差 → confident
  - 高均值 + 高方差 → mixed（需要 refinement）
  - 低均值 → poor（需要 rewrite + 重查）
  - 这个三档信号同时输入 conclusion prompt，让 4B 决策更可解释
  
  总结

  你不是"已经有 CRAG"，而是"有 CRAG 的两个组件中的简化版"：
  - ✅ Evaluator：reranker score + conclusion 决策
  - ⚠️  Query Rewriting：只改关键词，没改自然语言
  - ❌ Knowledge Refinement：完全没有
  - ➖ External Search：不需要
  
  真正能拿到 CRAG 收益的关键缺口是 Knowledge Refinement——chunk 级别的句子精炼。这也是我之前那张表里把它放
  Sprint 1（3 天工期）的原因，因为：
  - 不改训练
  - 不改索引
  - 只在 inference pipeline 加一步 reranker.score()
  - 立刻可见效
